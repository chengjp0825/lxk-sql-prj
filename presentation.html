The Problem

👤‍💻

Ghost Bookings

口头预约但无人使用，真正需要的人"一室难求"。信息不透明导致空间浪费。

⚠️

Double Booking

纸质登记或微信群调度，手动管理极易产生时间段重叠与冲突。

🔒

Management Black Box

管理员缺乏全局视角，无法实时监控使用状态或集中审批统筹。

The Solution

构建一个 可视化、自助式、强规则约束 的空间调度平台 — 透明、公平、极简。

Spec-Kit 工作流

Specification-first development pipeline — 6 standard commands

1 /speckit-specify → Generate spec.md from user description + quality checklist
2 /speckit-plan → Design technical implementation plan + constitution compliance check
3 /speckit-tasks → Break plan into atomic, dependency-ordered task checklist
4 /speckit-analyze → Cross-artifact consistency audit (spec↔plan↔tasks)
5 /speckit-implement → Execute tasks sequentially, mark [x] on completion
6 /speckit-git-commit → Auto-commit hooks after each phase (optional/mandatory)

Constitution 上下文约束

.specify/memory/constitution.md — 注入到每次 AI 调用的不可违背原则

📜 I. KISS 原则

拒绝过度设计、拒绝企业级架构。"以最少的代码让系统跑起来"

📦 II. 锁定技术栈

Vue 3 + Vite + Tailwind ← 前端
Python + Flask + SQLite ← 后端
禁止擅自引入其他技术

📁 III. 极简架构

前端三层（components/views/api）
后端两文件（app.py + models.py）
不引入 Pinia/Blueprint 除非必要

🔒 IV. 核心业务底线

时间段冲突判定 + 30分钟刻度轴
绝对不可省略或妥协

约束执行流:
Constitution → plan.md 的技术方案必须通过 "Constitution Check" 门禁
→ tasks.md 的任务分解必须符合架构约束
→ /speckit-analyze 自动检测违规

Gemini GEM 自定义上下文

Gemini 2.5 Pro 使用的 GEM 定义 — 固化 Spec-Kit 标准指令

📋 GEM 内容（关键片段）

你现在是"九号楼会议室管理系统"的全栈开发工程师。
你的核心开发哲学是 KISS (Keep It Simple, Stupid)。

# 1. 严格锁定的极简技术栈
- 前端框架：Vue 3 + Vite，必须使用 <script setup> 语法
- UI 与样式：核心使用 Tailwind CSS
- 后端框架：强制使用 Python + Flask
- 数据库：强制使用 SQLite + SQLAlchemy（ORM）

# 2. 极简代码与架构规范
- 前端目录仅保留 components / views / api
- 后端采用 app.py + models.py 两文件结构
- 前端状态管理优先使用 ref/reactive，不引入 Pinia
- 鉴权使用基础 JWT，不搞 RBAC

# 3. 核心业务底线（绝对不可妥协）
- 时间段冲突判定：必须实现严格的 Overlap 逻辑
- 半小时刻度轴：必须实现 30 分钟最小颗粒度时间轴

# 4. 代码输出要求
- 严禁输出 ... existing code ... 占位符
- 前端必须 npm run dev 可运行
- 后端必须 python app.py 可直接启动

🎯 GEM 的约束效果

GEM 将 Constitution 的核心原则 编译为 AI 可直接执行的指令。不同于 Constitution 作为"设计时的门禁检查"，GEM 在每一次代码生成时都强制 AI 遵循技术栈、架构、命名约定和交付标准。

Gemini + Claude Code 分工

G

Gemini 2.5 Pro

角色：规格制定者 (Specifier)

  • 接收用户原始需求描述
  • 生成 spec.md 用户故事 + 验收标准
  • 生成 plan.md 技术方案
  • 生成 tasks.md 原子任务分解
  • 运行 /speckit-analyze 一致性审计
  • 输入：GEM 上下文约束
C

Claude Code (Opus 4)

角色：实现执行者 (Implementer)

  • 接收 tasks.md 任务清单
  • 逐任务实现代码（写/编辑/构建）
  • 运行 npm run build 验证
  • 处理用户反馈和 Bug 修复
  • Git 提交 + 分支管理
  • 输入：CLAUDE.md + Constitution
工作流:
User → Gemini (GEM约束) → spec.md → plan.md → tasks.md → Claude Code (CLAUDE.md约束) → Code

关键经验

✅ 有效的

  • Spec-first 流程 — 规格先行避免了需求漂移
  • Constitution 约束 — 防止了技术栈蔓延和过度设计
  • AI 分工协作 — Gemini 做规划、Claude Code 做实现互补
  • 自动化 Git hooks — 每次 spec 变更自动提交/分支
  • CLAUDE.md 上下文注入 — CC 立即理解项目结构和当前任务
  • 质量检查清单 — specs/checklists 确保规格完整性

⚠️ 待改进的

  • UI 迭代过多 — 缺少 upfront 设计稿，靠反馈循环调整
  • 测试缺失 — 依赖手动验证，缺少自动化测试
  • 数据库迁移 — seed.py 简单但缺少版本化迁移
  • 移动端适配 — 目前仅桌面端
  • 时区处理 — 需要更健壮的 UTC/本地时间策略
