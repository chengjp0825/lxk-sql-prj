# Feature Specification: 九号楼会议室管理系统

**Feature Branch**: `001-meeting-room-booking`

**Created**: 2026-05-27

**Status**: Draft

**Input**: User description: "九号楼会议室管理系统 - 构建可视化、自助式、强规则约束的空间调度平台"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 空间雷达视图 (Priority: P1)

普通用户登录后，首页以楼层划分展示会议室看板，通过红绿灯颜色直观显示各房间当前状态。

**Why this priority**: 这是用户进入系统后的第一眼体验，决定了用户是否能快速判断"现在哪里有空房"。3秒钟内获得信息是核心价值主张。

**Independent Test**: 用户打开首页，无需任何操作，即可在3秒内判断目标楼层是否有空余会议室。

**Acceptance Scenarios**:

1. **Given** 用户打开系统首页，**When** 系统加载完成，**Then** 页面按楼层（如1F、2F）展示会议室列表，每个房间显示名称和当前状态色块
2. **Given** 某会议室已被预约且当前处于使用中，**When** 用户查看首页，**Then** 该房间显示红色占用标识
3. **Given** 某会议室未被预约或当前空闲，**When** 用户查看首页，**Then** 该房间显示绿色空闲标识
4. **Given** 某会议室被管理员停用，**When** 用户查看首页，**Then** 该房间显示灰色停用标识

---

### User Story 2 - 可视化预约 (Priority: P1)

用户选中空闲会议室后，在半小时颗粒度的时间轴上点击/拖拽选择时间段并提交预约申请。

**Why this priority**: 这是系统的核心交互流程，"像买电影票一样简单"是差异化价值所在。

**Independent Test**: 用户选定空闲会议室后，在时间轴上选择连续空闲时段并提交，系统返回预约成功确认。

**Acceptance Scenarios**:

1. **Given** 用户选中一个绿色空闲会议室，**When** 系统展示该房间的全天时间轴，**Then** 时间轴以30分钟为最小刻度，显示已占用和空闲区块
2. **Given** 用户在空闲时段上点击并拖拽选择连续时间段，**When** 选择范围完整显示在界面上，**Then** 用户可提交预约申请
3. **Given** 用户选择的时间段跨越已占用时段，**When** 用户尝试提交，**Then** 系统拒绝提交并提示冲突
4. **Given** 用户已选择时间段，**When** 提交预约申请，**Then** 系统记录预约并更新时间轴状态
5. **Given** 用户单次预约时长超过4小时，**When** 用户尝试提交，**Then** 系统拒绝提交并提示"单次预约最长4小时"

---

### User Story 3 - 管理员审批台 (Priority: P1)

管理员拥有独立控制台，可查看所有待审批申请并进行一键通过/驳回，也可将会议室设为停用状态。

**Why this priority**: 保障后勤部门对楼宇资产的绝对控制权，是系统可运营的必要条件。

**Independent Test**: 管理员登录后能看到所有待审批申请，执行通过/驳回操作后状态正确更新。

**Acceptance Scenarios**:

1. **Given** 管理员登录系统，**When** 进入管理后台，**Then** 系统展示所有待审批的预约申请列表
2. **Given** 管理员查看某条待审批申请，**When** 点击"通过"按钮，**Then** 该申请状态更新为已通过，时间段被正式占用
3. **Given** 管理员查看某条待审批申请，**When** 点击"驳回"按钮，**Then** 该申请状态更新为已驳回，时间段保持空闲
4. **Given** 管理员选中某会议室，**When** 点击"停用"按钮，**Then** 该会议室状态变为灰色停用，不再接受新的预约

---

### User Story 4 - 预约查询与取消 (Priority: P2)

用户可以查看自己的预约记录，并在条件允许时取消未开始的预约。

**Why this priority**: 用户需要对自己的预约有掌控权，取消功能是完整用户旅程的必要组成部分。

**Independent Test**: 用户进入预约记录页面，能看到自己的预约列表，并能成功取消符合条件的预约。

**Acceptance Scenarios**:

1. **Given** 用户已登录，**When** 进入"我的预约"页面，**Then** 系统展示该用户所有预约记录（含状态）
2. **Given** 用户有1条已审批且未开始的预约，**When** 用户点击"取消"按钮，**Then** 系统确认取消并释放该时间段
3. **Given** 用户有1条已开始的预约，**When** 用户尝试取消，**Then** 系统拒绝并提示"已开始预约不可取消"

---

### Edge Cases

- 用户尝试在时间轴上选择过去的时间段：系统应提示"不可预约过去时间"
- 用户同时打开多个浏览器标签页预约同一时段：后提交的请求应被拒绝（防冲突）
- 管理员将某会议室设为停用时，该房间有已审批的进行中预约：进行中的预约不受影响，新预约全部拒绝
- 用户预约时网络中断：前端应提示错误并允许重试，不产生孤立数据

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持用户登录/登出，登录后显示个人中心入口
- **FR-002**: 系统 MUST 在首页以楼层为单位展示会议室列表，每间会议室显示名称和实时状态（空闲/占用/停用）
- **FR-003**: 系统 MUST 为每个会议室提供可视化时间轴视图，时间轴以30分钟为最小刻度
- **FR-004**: 系统 MUST 禁止创建任何时间段重叠的预约（防冲突校验）
- **FR-005**: 系统 MUST 限制单次预约时长不超过4小时
- **FR-006**: 系统 MUST 支持用户提交预约申请，状态为"待审批"
- **FR-007**: 系统 MUST 支持管理员查看所有待审批申请并进行通过/驳回操作
- **FR-008**: 系统 MUST 支持管理员将会议室设为停用状态
- **FR-009**: 系统 MUST 支持用户查看个人预约记录
- **FR-010**: 系统 MUST 支持用户取消未开始的已审批预约
- **FR-011**: 系统 MUST 在用户操作冲突时返回明确错误提示

### Key Entities *(include if feature involves data)*

- **会议室 (Room)**: 代表九号楼内可预约的空间，包含名称、楼层、容量、状态（空闲/占用/停用）
- **预约 (Reservation)**: 代表一次预约记录，包含会议室、时间段（开始/结束）、申请人、状态（待审批/已通过/已驳回/已取消）
- **用户 (User)**: 使用系统的学生或教职工，包含用户名、角色（普通用户/管理员）
- **审批记录 (Approval)**: 管理员对预约申请的处理记录，包含操作类型（通过/驳回）、操作时间

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从打开系统到成功提交一个合规的预约申请，全程操作在30秒内完成
- **SC-002**: 系统必须实现绝对可靠的防冲突逻辑，任何时间重叠的预约单都不允许被创建（冲突率=0%）
- **SC-003**: 彻底消灭"双重预约"投诉
- **SC-004**: 首页加载后，用户能在3秒内判断目标楼层是否有空闲会议室
- **SC-005**: 管理员能在管理后台一键完成审批操作，单次操作不超过5秒

---

## Assumptions

- 用户通过校园统一身份认证或本地账号登录（具体认证方式待确认）
- 会议室的基础信息（名称、楼层、容量）由管理员预设，系统启动时已有初始数据
- 系统运营时间为每日 08:00-22:00，预约时间段不能跨越此范围
- 预约的最早可预约时间为当前时间后15分钟
- 每个用户同一时间段只能持有1个有效预约
