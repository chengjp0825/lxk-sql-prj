The Solution

构建一个 可视化、自助式、强规则约束 的空间调度平台 — 透明、公平、极简。

Spec-Kit 命令管线

6 步强制管线 — 从自然语言到可运行代码的结构化转换

1 /speckit-specify → 用户需求 → spec.md + 质量检查清单
2 /speckit-plan → spec.md → plan.md（技术方案 + Constitution Check）
3 /speckit-tasks → plan.md → tasks.md（原子化任务 + 依赖图）
4 /speckit-analyze → 交叉审计 spec ↔ plan ↔ tasks 一致性
5 /speckit-implement → 逐任务执行，完成标记 [x]
6 /speckit-git-commit → 每阶段结束自动提交

Spec-Kit × Git 联合妙用

每个 /speckit-* 命令前后自动触发 Git 操作 — 无需手动管理分支和提交

📌 before / after Hooks 机制

before hook → /speckit-specify → after hook → before hook → /speckit-plan → after hook → ...

📌 分支即设计 — 每个 /speckit 命令触发分支工作流

/speckit-specify → before hook → git checkout -b 003-feature-name → spec.md
（所有后续工作 —— plan、tasks、implement —— 都在此分支上）
↓
specs/003-feature-name/ 目录 + 所有代码提交 → merge 到 main

📌 三个关键 Hook

Hook触发时机Git 操作强制?
speckit.git.initializebefore constitutiongit init — 初始化仓库强制
speckit.git.featurebefore specifygit checkout -b 003-feature-name强制
speckit.git.commitafter 每个阶段git add -A && git commit -m "[Spec Kit] ..."可配置

📌 extensions.yml 配置示例

auto_commit:
  after_specify:  { enabled: true,  message: "[Spec Kit] Add specification" }
  after_plan:     { enabled: true,  message: "[Spec Kit] Add implementation plan" }

指令的严格约束

每个 /speckit-* 命令都有不可跳过的强制门禁

/speckit-specify

  • 最多 3 个 [NEEDS CLARIFICATION] 标记
  • 自动生成 checklists/requirements.md
  • 质量检查清单 必须全部通过，否则阻塞 plan
  • 用户描述 → 结构化用户故事 + 验收标准 + 成功指标

/speckit-plan

  • Constitution Check 门禁 — 拒绝过度设计
  • 技术栈锁定：Vue 3 + Flask + SQLite 不得擅自变更
  • 目录扁平化：前端三层 / 后端两文件
  • Phase 0 研究 → Phase 1 设计 → Phase 2 契约

/speckit-tasks

  • 强制格式：- [ ] [TaskID] [P?] [Story?] 描述 + 文件路径
  • 依赖关系图：标记 blocks / blockedBy
  • 并行标记 [P] 允许多 agent 同时执行
  • 按 User Story 组织，每个 Story 独立可测

/speckit-analyze

  • 交叉审计 spec ↔ plan ↔ tasks 三项一致性
  • Checklist 不通过 → 阻塞 implement
  • 检测未覆盖的需求、未分配的依赖

/speckit-implement — 最严格的执行阶段

  • 逐任务顺序执行 — 非 [P] 任务必须等前置完成
  • 每个任务完成后 必须标记 [x] 到 tasks.md
  • 任何非并行任务失败 → 整个管线中断
  • Phase 执行顺序：Setup → Tests → Core → Integration → Polish
  • 完成后强制触发 after_implement hooks（自动 commit）
  • 全程在 feature branch 上 — 从 specify 创建的分支开始，所有产物和代码都在同一分支上，不跨分支污染

Constitution × CLAUDE.md 双重约束

设计时门禁 + 运行时注入 — 确保 AI 在每一刻都遵守项目规则

🏛️ Constitution（设计时门禁）

I. KISS 原则
拒绝过度设计、拒绝企业级架构

II. 锁定技术栈
Vue 3 + Flask + SQLite — 禁止擅自引入

III. 极简架构
前端三层 / 后端两文件 / 不用 Pinia/Blueprint

IV. 核心底线
时间段冲突判定 + 30分钟刻度轴 — 绝对不可妥协

plan.md 的技术方案必须通过 Constitution Check，否则阻塞 tasks 生成

📋 CLAUDE.md（运行时注入）

<!-- SPECKIT START -->
- Implementation Plan: specs/xxx/plan.md
- API Contracts: specs/xxx/contracts/
- Quickstart: specs/xxx/quickstart.md
<!-- SPECKIT END -->

每次会话自动注入 — CC 立即知道：
• 当前活跃的 spec 目录和 plan
• API 契约和数据结构
• 项目启动方式和文件结构

关键经验

✅ 有效的

  • Spec-first 防漂移 — 需求在代码之前被锁定和审计
  • Git Hooks 自动化 — 零手动 commit，每个阶段可追溯
  • Checklist 质量门禁 — analyze 不通过 = implement 拒绝执行
  • AI 分工互补 — Gemini 规划 + Claude Code 实现，各司其职
  • Constitution 防蔓延 — 阻止了 Pinia/Blueprint/重型库的引入
  • CSS 变量体系统一 — 亮/暗主题切换零额外成本
  • CLAUDE.md 上下文注入 — CC 立即理解项目全貌

⚠️ 待改进

  • UI 迭代类任务 Spec-Kit 适配差 — "改好看点"无法结构化
  • 自动化测试缺失 — 依赖手动验证和构建检查
  • 数据库迁移方案简陋 — auto_migrate 能工作但不够健壮
  • 移动端未适配 — 目前仅桌面端可用
  • 时区策略需加固 — datetime.now vs UTC 的边界处理
